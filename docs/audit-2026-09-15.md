# Comprehensive project audit — September 15, 2026

## Overall assessment

**The project is running reliably and its core accounting is sound, but it needs targeted correctness and reliability fixes.** The strongest parts are its preserved forecast evidence, separation of opinions from measurements, failed-fetch handling, and reproducible publication. The most consequential confirmed defects are incorrect gearing ceilings, impossible duplicate-item upgrades, and transcript recovery selecting an older reservation over completed results. Publisher-date reporting also hides the age of Method's opinions.

This is an inspection report, not a remediation release. No application code, provider data, repository settings, workflows, or dependencies were changed by this audit. Audit documentation and sanitized verification evidence are the only intended repository additions.

## Findings, ranked for action

Priority P2 means a material correctness or reliability fix; P3 means a narrower reporting or coverage fix. S1 is a separate security architecture finding with an untested full attack path.

### F1 — P2: Gearing's item-level ceilings omit upgrade tracks

**Impact:** Valid upgrades disappear, and the recommendation sheet understates how high an item can go.

`maxAttainable()` in `gearing/src/app.template.html:1860` uses raid drop levels and the M+ starting Vault level as the maximum. Those numbers are labeled “Ceiling” and filter upgrade candidates at line 1987.

The current item `268236` is stored as **334, Myth 6/6**, but its computed ceiling is **318**. **54 raid gear rows** have a stored tooltip level above their computed maximum. The [current Icy Veins upgrade table](https://www.icy-veins.com/wow/world-of-warcraft-gear-upgrading-guide) independently lists Myth 1 at 318 through Myth 6 at 334.

**Live reproduction:** Select Frost Mage and import `legs=,id=268236,ilevel=324`. The ordinary upgrade list says no Season 2 source exceeds 324 for that slot. Separately displayed direct-tier routes do not correct the excluded ordinary candidates.

**Correction:** Model acquisition level and maximum upgrade level separately; use the appropriate value in filters, potential, and labels. Preserve the documented 344 final-boss exception. Add a regression that checks the calculation against the actual stored track, rather than restating the formula.

### F2 — P2: Unique-Equipped conflicts produce impossible upgrades

**Impact:** The checker recommends a ring already equipped in the other slot, and loot-source potential counts an impossible gain.

`gearing/src/app.template.html:1885` admits same-slot candidates; line 1986 filters only by level. Lines 1685–1694 reduce paired slots to their lowest level, losing the equipped item identities needed by the potential calculation at line 1724.

**Live reproduction, Frost Mage:**

```text
finger1=,id=268249,ilevel=324
finger2=,id=268252,ilevel=280
```

Finger 2's first recommendation is another Vile Alchemist's Band (`268249`). The current data and [item page](https://www.wowhead.com/item=268249/vile-alchemists-band) mark it Unique-Equipped. A pure artifact calculation assigns this impossible replacement **+44 potential**.

**Correction:** Evaluate replacements against the complete equipped loadout. Permit upgrading/replacing the existing copy while refusing a second conflicting copy. Apply the same eligibility function to the upgrade checker and loot-source potential, including trinkets and applicable weapons.

### F3 — P2: Transcript recovery restores an older reservation over completed results

**Impact:** Successful API fetches lose their completed bookkeeping/cache state and become falsely uncertain, undermining recovery after an interrupted publication.

`src/restore-transcript-state.mjs:31–33` assumes artifact IDs increase chronologically and picks the largest. Actual receipts disprove that assumption:

- September 12 reservation `10299107612` preceded completed artifact `10298937863` despite having a larger ID.
- The completed receipt records video `rYFv6Ohr7mE` fetched successfully, with 303 caption chunks, encrypted cache present, and zero uncertain requests.
- [September 13 run](https://github.com/riles22/wow-class-tracker/actions/runs/34763247234) restored the older reservation. `prepareBatch()` (`src/transcript-state.mjs:84`) then marked the successful request `review-required`.
- [September 14 run](https://github.com/riles22/wow-class-tracker/actions/runs/34869052776) retained one falsely uncertain request and again selected the preceding day's reservation over its completion.
- September 14 repeats the ordering inversion: reservation `10358492062` at 16:33:10Z, completion `10358447261` at 16:33:11Z.

The queue is currently drained. **No duplicate billing or current missing published content was established.**

**Correction:** Select trusted run/attempt and completed-versus-reserved phase using explicit chronology/phase metadata, not numeric ID magnitude. Preserve interrupted-run reservations when no completion exists. Reconcile the erroneous request from its successful receipt, without purchasing another transcript. Test reversed IDs and interrupted attempts.

### S1 — Security isolation gap: “trusted” evidence shares the agent's runner

**Confirmed architecture gap; full attack path untested. No compromise was observed.** This warrants a focused security fix before extending unattended agent authority.

The deterministic collectors, their evidence uploads, and the unrestricted shell-capable agents execute in the same `refresh` job (`.github/workflows/nightly.yml:77`, `:102`, `:232`). The same cached upload action executes again after the agent at lines 534–550. Publication retrieves trusted evidence by **name** at lines 605–632 rather than producer IDs/digests held outside that execution environment.

Independent review of the exact pinned [upload action](https://github.com/actions/upload-artifact/blob/043fb46d1a93c77aae656e7c1c64a875d1fc6a0a/src/upload/upload-artifact.ts) and its bundled toolkit confirms same-job delete/reupload support. It uses an Actions runtime token distinct from the restricted GitHub token. The [runner provides runtime credentials to Node actions](https://github.com/actions/runner/blob/main/src/Runner.Worker/Handlers/NodeScriptActionHandler.cs); source pinning does not protect cached action files from another process in the same writable job.

**Inference:** A prompt-injected agent able to alter later action execution could replace a named pre-agent receipt alongside matching data. Schema/content gates would still run, but their supposedly independent evidence could then be controlled by the same actor. No artifact replacement or service exploit was attempted. The existing documentation's “no tamper window” assurance is therefore stronger than the implemented isolation supports.

**Correction:** Move deterministic collectors/evidence uploads into a separate job without agent execution. Pass producer artifact IDs and digests directly to publication through trusted job outputs and reject missing/mismatched receipts. Retain read-only agent GitHub permissions and the existing publication gates.
