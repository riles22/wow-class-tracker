## Findings, in remediation order

### F1 — P1: Agent-controlled log filenames reach a privileged shell

**Location:** `.github/workflows/nightly.yml:582–587`; artifact admission at `:419–423`, privileged job at `:433–436`, and staging at `:700`.

The skill-log churn check obtains filenames from Git and interpolates each into `execSync`'s command string. An unusual filename can therefore be interpreted by the shell rather than passed literally to Git. This check runs in the publish job with repository, Actions, and issue write permissions and a credentialed checkout.

The surrounding controls do not close the route: new skill-log paths travel in the wildcard artifact, the new-file refusal covers `data/` only, and the wildcard staging command admits a new log. A new untracked log is absent from the first run's `git diff`; once committed, a later modification reaches the shell-interpreted read. This is a two-run path requiring influence over refresh output, not an unauthenticated command endpoint on the static website.

**Evidence:** an audit agent used an isolated Git repository and a harmless marker-file action to demonstrate admission on the first run and command execution on the second. The lead reviewed the actual workflow's admission, comparison, staging, and permission paths, and verified that the same workflow blob is deployed on master. No production credentials or workflows were exercised. No evidence of prior exploitation was established.

**Fix:** replace the interpolated shell command with `execFileSync('git', ['show', 'HEAD:' + file], ...)`; obtain filenames using NUL-delimited Git output without trimming; allow only the existing intended skill-log paths and reject additions. Test literal filenames containing spaces and shell metacharacters, and reject unauthorized new log paths. Preserve the chosen warning-only policy for legitimate log-content pruning; the defect is filename execution, not that policy.

### F2 — P2: A failed forced guide refresh overwrites usable source data and reports success

**Location:** `gearing/src/lib-guide-runner.mjs:27–32,46–54`.

`--force` starts with an empty source instead of retaining prior records. Retrieval failures are caught as absent entries, and the partial or empty result is written over the source without a failing exit status. This conflates a transport failure with a verified absence.

**Reproduction:** on a temporary copy of the current guide source, simulate HTTP 403 for all 40 specs and run the real runner with `--force`. It resolves successfully with **zero saved spec records and 40 absent records**. The real guide-payload builder accepts the resulting missing Icy Veins source because the other guides still provide builds. On current data that loses **315 candidate cells** and lowers **726 per-item consensus counts**, while the source remains listed.

**Fix:** refresh into staging, retain prior observations on retrieval errors with honest dates/status, distinguish verified absence from failure, and return failure for an incomplete forced refresh. Promote only a validated result. Test all-failure and partial-failure runs through both harvesting and downstream build acceptance.

### F3 — P2: The gearing game plan overstates upgrades for weapons that cannot replace the off hand

**Location:** `gearing/src/app.template.html:1674–1680`.

The plan treats every `One-Hand` item as eligible to replace whichever equipped hand has lower item level. The existing `matchingWeaponHands` rules correctly know that some weapons can replace only the main hand, but this calculation bypasses them.

**Reproduction using published items:** set main hand to 344 and off hand to 280. Holy Paladin's Baleful Hexblade (268211) and Frost Mage's Jan'thrazet (271092) each report **+64 potential instead of 0**. Protection Warrior's Thorned Reply (251195) reports **+38 instead of 0**. In each case the project's curated loadout permits that item in `mainHand` only. The calculation can therefore send a user toward a boss or dungeon for a nonexistent upgrade.

**Fix:** derive eligible replacement hands from `matchingWeaponHands(CUR, item)` and the active equipped loadout. Test caster offhands, shields, legitimate dual wield, and two-hand replacements. These are project-data reproductions; no equipment rules were supplied from model memory.

### F4 — P2: A no-op or partial guide harvest makes the whole source appear newly fetched

**Location:** `gearing/src/lib-guide-runner.mjs:27–39,53–54`.

The runner stamps today's `harvestedAt`, then skips existing records by default. It still rewrites the source with today's date. A one-spec refresh similarly advances the source-wide date, which is consumed by the freshness gate and visible guide-source labels.

**Reproduction:** with the current complete Icy Veins source, the runner made **0 fetch calls**, retained all **40 records identically**, and changed `harvestedAt` from **2026-08-31 to 2026-09-05 UTC**. The audit was performed September 4 Pacific time.

**Fix:** make a completed no-op truly leave the file unchanged. Record verification dates per spec and derive source freshness from required coverage rather than the newest attempt. Preserve publication dates separately. Test zero-fetch resumes, one-spec refreshes, and mixed-age coverage.

### F5 — P2: A benign repeated freeze overwrites the original forecast provenance

**Location:** `src/snapshot.mjs:174–189`.

The retry guard compares cells and version fields, intentionally ignoring changing Git/data hashes. It then unconditionally rewrites the existing artifact. An otherwise harmless retry can replace the original `gitSha`, `dataSha256`, and source-date receipt even though the forecast itself is identical.

**Reproduction:** freeze a temporary copy, add an unrelated data JSON file, and freeze the same date again. Cells remain identical, but the artifact's data hash changes and its original bytes are replaced.

**Fix:** accept equivalent retries by retaining the existing artifact bytes. Continue refusing changed forecast substance. Add a regression test where a changed run manifest or Git commit does not alter an existing declaration. The current committed August 11 record passed the integrity checks above.

### F6 — P2: Between cycles, validation allows retired PTR metrics to be retagged live

**Location:** `src/validate.mjs:335–343`.

The rule rejecting a PTR-named metric with `era: 'live'` depends on `PHASES.ptr` being active. The separate between-cycle rule rejects a missing era, but permits an explicitly wrong one. Client rendering trusts the explicit era.

**Reproduction:** in a cloned current dataset, change Blood DK's `Median rDPS (12.1 PTR M+ testing, tank)` from PTR to live and run full-roster validation. It returns **zero errors** while the cycle is closed. All **267 current PTR metrics are correctly tagged**; this is a missing guard, not current data corruption.

**Fix:** require `era === 'ptr'` whenever the name contains the PTR token, independently of the current marker. Add tests for both the active and closed-cycle states, including old PTR markers after a new cycle opens.

### F7 — P2: The approved on-page forecast report card has not been completed

**Location:** `docs/s2-transition-scope.md:83–89` (Decision 2); `src/template.html:3397`; report-card CLI in `src/report-card.mjs`.

The approved scope promises an on-page grade chip and linked report at the +14-day settled checkpoint. The CLI now grades **August 11 → September 1**, but build/template do not consume that grade, the linked full report has not been produced, and the public forecast comparison still says **“not yet a grade.”** That comparison against today's data is a different object from the settled grade and should remain distinct.

**Completion:** generate the settled report from the frozen/settled pair, disclose its endpoint and coverage, expose the result on the forecast header, and link the report. Keep the original forecast immutable and preserve the +28-day comparison as a separate checkpoint. This requires finishing the approved display feature, not retuning the forecast.

### F8 — P2: Human metric-move approval is missing from both refresh completion checks

**Location:** `.github/workflows/nightly.yml:280–292,359–372,650–658`; `src/check-refresh.mjs:683`.

The dispatch input `value_move_ack` is supplied to publish Gate 3 but not to the primary or final refresh completion checks, although all call the same gate. An approved large metric change can therefore launch unnecessary recovery and leave refresh red for the very change the operator approved.

Publish explicitly runs even after refresh fails, so this does **not** necessarily prevent deployment. The concrete problems are wasted recovery work and a misleading failed refresh/workflow state.

**Fix:** pass the same human input as `VALUE_MOVE_ACK` to both deterministic completion steps. Keep it out of agent-owned data and separate from `ANOMALY_ACK`. Test consistent acceptance across all three call sites.

### F9 — Policy inconsistency: The Archon outage note says three-source consensus, but the product uses four

**Location:** `data/required-sources.json:143`; `src/normalize.mjs:163–167`.

The outage note says Archon is dropped from consensus during the wall. Runtime eligibility checks season, not freshness; its stored August 25 S2 letters still contribute to **all 80 local consensus cells**. The browser correctly describes the result as four-source consensus.

This is material: excluding Archon in memory changes **24/80 letters**, including Frost DK raid B/54 → A/63 and Discipline raid A/72 → A+/87. It does **not** prove that automatic exclusion is the right policy. Retaining dated observations during an outage may be intentional.

**Decision needed when remediating:** confirm retention versus expiry, then make contract prose, freshness treatment, and visible explanation agree. Do not silently remove Archon as an audit cleanup; changing source composition requires the established version/movement safeguards.

### F10 — P3: The CLI labels an accepted grade “NOT COMPARABLE”

**Location:** `src/report-card.mjs:425`.

Every warning is given that prefix, including an expected consensus-version change. The current grade has recorded matching source composition and returns `comparable: true`; the CLI nevertheless labels its 3→6 version disclosure “NOT COMPARABLE.”

**Fix:** distinguish informational disclosures from comparability refusal and add a CLI-output assertion. Correct this before exposing the report under F7.

### F11 — P3: Rounded scores can contradict the visible letter thresholds

**Location:** `src/normalize.mjs:225–226`.

The letter is computed from the raw mean, then the displayed score is rounded. Current Mistweaver M+ is **B / 58**, although the legend says A starts at 58; the raw mean is 57.5. The arithmetic is sound, but its displayed precision hides the reason for the letter.

**Fix:** disclose fractional precision where score and letter are compared. Do not change consensus boundaries simply to make rounded numbers agree. Add a half-point boundary presentation test.

### F12 — P3: Gearing's Loot sources panel widens the phone page

**Location:** `gearing/src/app.template.html:1796–1800`.

At 390px with Holy Paladin selected, opening Loot sources increases document width to **494px**. The other four panels remain at 390px. Its five-column tables lack the contained scrolling already used by Item levels.

**Fix:** use the existing table-scroll container or a stacked mobile layout. Add a real-browser check opening every disclosure panel at phone width.

### F13 — P3: Keyboard sorting loses focus

**Location:** `src/template.html:2388–2405` and the `.hsort` activation path.

Focus a column-sort button and press Enter. Sorting replaces the matrix, including the focused button, and `document.activeElement` becomes `BODY`. Keyboard users lose their place each time they sort. Existing tests exercise sorting results without asserting focus continuity.

**Fix:** remember the activated sort key and focus the replacement button after render; verify both Enter and Space without moving focus during unrelated updates.

## Efficiency and maintainability

The computational core is already fast. Twenty current-data payload builds measured **8.23ms median / 10.51ms p95**, excluding input cloning. Gearing's 40 successive spec selections took approximately **0.9–1.0 seconds total** on this desktop. A framework migration or new runtime dependencies would add work without addressing a measured bottleneck.

These compressed sizes are local measurements, not a promise about CDN transfer size. The public response did use gzip. In one local-file Chromium sample, tracker desktop first contentful paint was **224ms** and DOM ready **212ms**; at 390px with **4× CPU throttling**, first contentful paint was **376ms**, DOM ready **850ms**, and the largest recorded startup long task was **341ms**. These are synthetic diagnostics, not field Core Web Vitals or a complete network benchmark.

Useful optional work after correctness fixes:

1. **Trim only unused data from the generated browser payload.** Serialized creator takes/meta notes account for about 799k characters, spec build-change detail 229k, and the full patch feed another 174k. Some duplication serves real surfaces. Measure a slimmer render payload while retaining canonical source data, citations, archive receipts, credits, and offline use. The prior audit already left payload slimming open; this is updated sizing, not a newly discovered defect.
2. **Keep lazy drawer construction.** Initial tracker DOM was about 2,570 elements; opening all 40 drawers created about 17,909. Building those drawers took 120ms normally and 757ms at 4× throttle. The stress case supports preserving the current on-demand behavior.
3. **Add tests at the boundaries that failed.** Prioritize shell-free filename handling, staged/failed guide promotion, per-record freshness, weapon-hand eligibility, immutable retry provenance, explicit PTR era, phone disclosures, and keyboard focus. More tests that simply restate helper formulas will not catch these failures.
4. **Reduce duplicated operational instructions when next touched.** The ignored local AGENTS/skills mirror and tracked instructions already had documented drift in the previous audit. Keep current code, tracked procedures, and dated decision records easy to distinguish. Do not treat historical comments or hand-maintained coverage counts as current measurements.

These are existing owner follow-ups from the security audit, not evidence of compromise or replacements for fixing F1. The current CLI report covers **80/80 cells**, **41% exact letters**, and **89% within one band**. Its Spearman ordering exceeds the carry-forward baseline in all six role/bracket groups at the September 1 endpoint. This grades agreement with the selected publisher-consensus snapshot, not objective game performance; the comparator also contains dated observations from the known outages. No exhaustive live re-harvest, source-by-source factual recertification, credential audit, Firefox/Safari run, physical-device test, assistive-technology audit, or destructive recovery exercise was performed.
