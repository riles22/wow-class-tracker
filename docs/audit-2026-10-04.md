## Findings, ranked for action

### F0 — P1: The live WCL client secret is publicly readable

**Impact:** Anyone can download the Warcraft Logs client ID and secret that the nightly's WCL collection uses. Whoever holds them can spend the client's API allowance (3,600 points an hour), which the nightly, the owner's local tools and the owner's other projects all share.

- A commit from July 9 was force-pushed off `master`, but GitHub still serves it to anonymous requests, including a copy of the local WCL config file. At the final check (October 5, UTC) the commit API, the blob API and the raw file URL each returned HTTP 200 without authentication. The commit ID is kept in the owner's private notes, not here.
- Both values equal today's local config, compared by SHA-256 and never printed. Both local copies were last written on July 2.
- The Actions secrets `WCL_CLIENT_ID` and `WCL_CLIENT_SECRET` were last updated on July 7. That they hold the same client is inferred from that date; Actions secrets cannot be read back.
- Secret scanning shows 0 alerts because GitHub has no pattern for WCL credentials. This audit's security lane scanned reachable history only. The same-day workspace audit found the commit by scanning every object.
- `docs/audit-2026-07-24.md` says twice that history holds no secret: in its Security introduction and in its supply-chain bullet. That has been false since July 9.
- No branch or tag here reaches the commit; the local clone keeps it only as an unreferenced object.
- Treat the credential as already copied. Commits removed by force-push from public repositories are routinely recovered from the public event archive. Whether anyone used it is unknown.

**Correction:**
- **Owner, in the WCL portal, before the next nightly if possible:** create a replacement client, preferably one per consumer (GitHub Actions, local tools, each other project). Update the two Actions secrets and both local `refresh-metrics/config.json` copies.
- Dispatch `wcl-probe.yml` and confirm it is green on the new client.
- Then revoke the old client, at a time when no nightly is running. Revocation is the step that closes the exposure; removing the commit does not undo a copy already taken.
- Optionally, ask GitHub Support to remove the unreachable commit.
- Add a dated correction to `docs/audit-2026-07-24.md`.
- Future secret checks scan every object, including unreachable ones (`git cat-file --batch-all-objects`), not only reachable history.
- Keep this document uncommitted until the old client is revoked.

### F2 — P2: The anomaly gate cannot see one outlet rewriting its whole list

**Impact:** The gate documented as the defense against a corrupted tier list passes the exact shape it is named for. One outlet's bad parse reaches the consensus diluted to about a quarter of its size, so it stays under the limits.

The measured threshold is **more than 25 changed letters, or more than 10 two-step changes, on the source's own scale.**
- It fires on 0 of 63 commits since August 20, including the early-Season-2 churn of August 22–25 and the September 27 Icy Veins catch-up.

- Do not use the first proposed threshold (more than 20 letters or more than 8 two-step). It would have reddened three real nightlies (August 22, 24 and 25) and the September 27 Icy Veins catch-up.

Correct the two documents. Because the measured threshold is safe, this can land before launch week. It is a gate-contract change, so it needs owner review.

### F4 — P2: The gearing upgrade checker ignores the item levels in real /simc exports

**Impact:** "Your potential" and the per-slot upgrade steps show "—" for every slot of a real export. The feature works only for hand-typed or synthetic pastes, which is what the tests use.

- `gearing/src/app.template.html:2082-2083` reads an item level only from an `ilevel=NNN` token. Without one the level is null, and `:538` defaults the manual field to 292. `:1738` already says pastes without `ilevel=` are the common case.
- The SimulationCraft addon (`core.lua` 619–623 and 1264–1268) writes the level in a `# <Name> (<ilvl>)` comment above each item line and never emits `ilevel=`.
- Reproduced in Playwright with a three-slot Frost Mage export in the addon's real format:
  - every level came back null;
  - the hint read "3 slots read · 0 with item levels";
  - every potential cell showed "—".

**Correction:**
- Bind the most recent `^#\s*(.+?)\s*\((\d{3})\)\s*$` comment to the next slot line, and keep an explicit `ilevel=` as an override.
- Add a verbatim addon export as a fixture. Include the `### Bags` section, which must not be read as equipped gear, and the `# Checksum` line.

### F5 — P2: Gearing counts a catalyzed tier piece and its base item as two candidates

**Impact:** Agreement is undercounted on the five tier slots. In 110 slot cells across 26 specs, Wowhead votes for the base item while Icy Veins (and sometimes Method) vote for the catalyzed tier piece, so the client sees two candidates.

A conservative merge, counting only cells where Icy Veins names the same base, would add a source to 85 base candidates in 24 specs. It would change 80 headline chips and 8 headline picks.

No value is invented, and the tier piece never appears as a phantom row on the sheet. Its stranded vote shows only as a "1/3 (tier)" chip in the Loot sources panel.

- **The convention exists in one harvester.** `harvest-guide-wowhead.mjs:107-110` keys catalyzed rows by their base item; its comment explains that the base is what actually drops.
- **The other two harvesters ignore it.** Neither reads `original-item`:
  - Icy Veins takes the first `item=` (`harvest-guide-icyveins.mjs:95-96`);
  - Method uses `item=(\d+)` (`harvest-guide-method.mjs:56`).
- **The client cannot reconcile them.** `consensusOf` (`app.template.html:823-838`) merges only on an exact item id.
- **Icy Veins' markup does carry the base,** for example `item=271456&bonus=12854&original-item=268229`.
- **The two are not always the same item.** In 85 of the 110 cells, Icy Veins names the same drop source as Wowhead's base. In 23 it names a different one; Holy Paladin Head is one of these.
- **110 is a floor.** Protection Warrior Legs is split although Wowhead has no catalyzed row there.

**Correction:**
- Have the Icy Veins harvester read `original-item` on each row and key by the base, as Wowhead does.
- Do not merge on the tier piece. One tier piece maps to several bases, even within one Icy Veins page, and merging would invent agreement in the 23 differing cells.
- Method publishes no `original-item`, so its tier-piece votes (stranded in 51 cells) need an owner policy: map by source text, drop them, or leave them.
- Re-harvesting Icy Veins needs a local run.
- Fix this together with F6: the 15 attribute-order rows F6 recovers include 10 catalyzed base rows, which would otherwise become new split cells.

## Verification limits and evidence

- **Read-only.** The replays, the rehearsal and the coverage runs used scratch clones and `git archive` exports. No push, dispatch, credentialed WCL collection or paid transcript request was made. Scratch scripts and outputs are kept outside the repository; the key commands are given inline.
- **Publisher access was limited.** Icy Veins and Wowhead returned 403s to several verification fetches on October 4. F5 and F6 therefore rest on same-day page captures; four independent captures each of the Holy Paladin, Shadow and Enhancement pages have identical guide-body hashes.
- **Browser checks** were Playwright runs against local builds and the deployed pages. They are not screen-reader, physical-device, real-character or in-game validation.
- **Forecast measurements** cover one cycle of about 80 correlated cells. Every candidate weight was chosen after the outcome was known, which is why F34 recommends pre-registration rather than adoption.
- **Second-pass figures win.** Where the second verification measured differently from the first pass, the second figure is used. Examples: `seasonVerified` history 22/25 rather than 24/26 (URL re-points), and degraded-pair counts 1,098 rather than 122 (a different method). No conclusion changed.
- **Sub-agent output was treated as data.** Text inside it that resembled harness or permission directives was not acted on.
- **Secret scanning missed F0.** This audit scanned the working tree and reachable history only; the same-day workspace audit found the unreachable commit. F0 was re-verified here with anonymous requests and hash comparisons that never printed a value. Whether the credential was used is unknown, and the Actions secrets cannot be read back.
- **Not in the baseline:** PRs #84 and #85 were opened during the audit and are not part of it.
